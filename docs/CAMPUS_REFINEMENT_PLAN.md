# 西大三维校园精细校准实施计划

> 编制日期：2026-09-12
>
> 依据：用户提供的 6pro《西大项目优化建议》，以及编制时仓库 `10b631d` 的源码、数据与文档。
>
> 状态：计划已建立，现按阶段实施。完成情况与实测结果见 [执行记录](CAMPUS_REFINEMENT_PROGRESS.md)；下文保留编制时的基线和验收要求。

本轮目标是提升校园的地点辨识度和空间可信度：让普通楼栋拥有有依据的高度、形制和入口，让建筑、铺地、道路与绿化自然连接。首轮交付聚焦三件事：**统一普通建筑远近景形体、校准 20–30 栋普通建筑、完成图书馆北入口周边场地样板。**

## 1. 编制基线与范围

以下数字来自编制时的 `public/data/`，用于实施前后比较；既有文档中的历史数字不直接作为当前基线。

| 项目 | 编制时状态 | 本轮处理原则 |
| --- | --- | --- |
| 建筑 | 448 栋：校内 435 栋、紧邻校界 13 栋 | 保留稳定 ID、已有轮廓、内院及校外范围约束 |
| 高度依据 | 347 栋按类型估算，约占 77.5% | 逐栋补充依据；其余建筑也不一概视为实测 |
| 精选地标 | 20 处，已有独立模型和导航 | 保留既有地标身份与导航范围 |
| 普通建筑加载 | 30 个约 360 米空间区块，基础与近景替换 | 沿用分块、实例化、卸载及预算机制 |
| 地形 | 125 × 165 网格，米制坐标，保留原始高程 | 保留大地形；局部平台、坡道、岸边单独表达 |
| 示意植被 | 3,034 株，已有远近模板与多轮排树约束 | 优先校准空间分布和留白 |
| 首屏模型体积 | `base + trees` 为 5,051,912 bytes | 保持现有不超过 6,000,000 bytes 的检查 |
| 最大普通近景区块 | 1,708,364 bytes | 保持单块小于 2,000,000 bytes 的检查 |

本轮不扩展校园边界、不程序化补楼，不重写引擎或加载系统，也不以整体 DEM 加密、随机楼高和全校高模树替代资料校准。保留已完成的运动场平整、主路铺装、农院路上下分层、桥洞裁剪及六处下穿接口。

编制时源码中可直接确认的改进入口（后续修复状态见各阶段及执行记录）：

- `category()` 将宿舍、餐厅、公寓归为 `living`，而 `generic()` 又据此生成阳台；用途与形制需要分开。
- 普通建筑入口默认取外环最长边中点；窗层数在生成器内按 `height / 3.3` 再推导，需要与校准层数统一。
- 部分低矮、轴对齐矩形普通建筑只在 `detail` 分支生成坡屋顶，存在基础与近景轮廓不一致的规则。
- 剩余通用铺地仍使用道路抬高 0.40 米、其他非水面抬高 0.26 米的显示偏移；是否产生可见悬边须逐处检查。

上述是源码与数据诊断。树位观感、入口衔接效果及真实性改善，需要后续固定镜头与资料对照验证。

## 2. 优先级、阶段与依赖

| 阶段 | 优先级 | 工作包 | 交付物 | 完成条件 |
| --- | --- | --- | --- | --- |
| S0 | 前置 | 建立基线、样板边界与候选楼栋清单 | 镜头清单、资产指标、20–30 栋候选记录 | 当前画面可复现，每栋候选有稳定 ID 和待核对字段 |
| S1 | P0 | 统一普通建筑基础与近景形体 | 共享形体规则、屋顶修复、专项回归 | 主要轮廓不随细节级别改变，屋顶不由世界坐标轴方向决定 |
| S2 | P1 | 建立楼栋校准表并完成首批校准 | 字段契约、5–8 栋试点、随后扩展至 20–30 栋 | 每项校准有依据，默认规则与人工覆盖均可追溯 |
| S3 | P1 | 图书馆北入口完整场地样板 | 场地参数、连接几何、绿化留白、对照图 | 道路到入口连续，周边体量合理，远近景和性能验收通过 |
| S4 | P2 | 植被分区与局部场地推广 | 行道树/庭院/开放区域规则、代表性岸段 | 有资料区域按空间组织，无资料区域继续明确标为示意 |
| S5 | P3 | 材质和小构件细化 | 通过预算检查的局部细化 | 已通过形体和场地验收，新增细节有可见收益 |

执行顺序：**S0 → S1 → S2 试点 → S3 样板验收 → S2 扩展及 S4 → S5。** S0 完成后，楼栋资料整理可与 S1 并行；S3 的资料和边界整理可与 S2 并行。修改共享数据准备流程时应串行集成，避免不同工作包覆盖派生数据。

首轮完成范围为 S0、S1、S2 的 20–30 栋校准及 S3；S4、S5 作为随后推广任务，不阻塞首轮交付。排期以资料到位情况和试点构建成本为依据，暂不承诺未经评估的完成日期。

## 4. S1：先修正远近景形体

**主要入口：** [blender/build_campus.py](../blender/build_campus.py) 的 `generic()`，以及 [blender/geometry.py](../blender/geometry.py)。

- [x] 将普通建筑生成拆成“解析最终形体参数 → 构造共享主体 → 按细节级别附加构件”；保持现有导出与区块替换机制。
- [x] 在本阶段先确定共享形体的最小内部结构，接入现有参数和保守屋顶默认值；S2 在相同结构上增加人工覆盖输入，避免屋顶修复等待全部资料整理完成。
- [x] 基础和近景共用现有主体高度、屋顶类型、屋脊方向、庭院及影响轮廓的主要入口构件。资料约束的主楼/附楼多高度分段仍属于 S2，S1 验收时 `parts` 为空，不计作已完成校准；S2 试点已开始接入分段，见楼栋校准记录。
- [x] 移除“高度低、矩形且轴对齐就应有坡顶”的判断。无屋顶依据时采用明确标为推定的默认平顶；有依据时两个级别都生成对应简化屋顶。
- [x] 坡顶沿建筑局部方向生成，支持旋转后的矩形；现有复杂轮廓采用受原轮廓约束的坡面，保留内院或凹口。资料明确的多高度分段在 S2 接入。
- [x] 细窗框、窗梃和细栏杆由近景增加；影响主体识别的屋顶、雨棚、平台保留基础表达。瓦纹及小装饰尚未新增。
- [x] 完整重建 `.blend`、`base.glb`、受影响近景区块与 `models.json`，同步资源哈希。

验收使用旋转矩形、带内院、凹形、带附楼以及当前屋顶规则命中的实际普通建筑作为样本。比较共享主体的高度、屋脊、体量分区和内环，并在网页中反复加载、卸载近景。不得出现平顶变坡顶、主体增高、内院被封或整栋短暂消失。

几何检查应比较共享主体或语义构件，不能要求包含窗框和栏杆的完整包围盒逐点相同；导出检查需考虑 Draco 量化误差，并在报告中明确容差依据。

## 5. S2：楼栋校准数据与首批 20–30 栋

### 5.1 最小数据契约

建议新增人工维护的 `data/building-overrides.json` 和小型解析模块 `scripts/building_overrides.py`，由 `scripts/prepare_geodata.py` 在建筑标准化过程中调用。公共 JSON 继续作为派生产物，不直接手改生成结果。

| 字段 | 用途与约束 |
| --- | --- |
| `schemaVersion` | 标明校准表结构版本 |
| `buildings` | 以现有 `way/…`、`relation/…` 为键；名称改变不换 ID |
| `archetype` | 建筑形制；首版只实现样本需要的 `dormitory`、`canteen`、`teaching-block`、`courtyard-lab`、`low-rise-service` 和 `generic` |
| `levels`、`floorHeight`、`height` | 分别记录层数、采用层高及主体高度；每项独立标明依据，避免层数确认后把层高也当实测 |
| `roof` | 类型、相对主体的抬升、坡度或屋脊方向；屋顶增量与主体高度分开，避免重复计高 |
| `parts` | 可选的主体、附楼、裙房等分段；约束在既有轮廓内，保留内环，首版不做通用建模语言 |
| `entrances` | 入口 ID、米制位置、朝外方位、宽度、主次及依据；入口需锚定具体外立面 |
| `facadeRules` | 有依据的实墙面、窗列及阳台开关；按立面局部线段定位，并检查其仍落在当前轮廓上 |
| `evidence`、`sourceRefs` | 对应到具体字段的资料 ID、确认/估算/待核对状态、说明与日期；接入现有来源目录 |
| `footprintRevision` | 保存校准时轮廓摘要或 OSM 版本，提示后续轮廓更新造成的入口/立面锚点失效 |

坐标采用数据和 Blender 的本地米制：X 向东、Y 向北、Z 向上。新增入口方位约定为正北 0°、顺时针递增；调用既有局部旋转函数时明确转换，网页仍沿用现有 X 东、Y 上、Z 南的映射。

`category` 继续用于用途分类和现有导航；`archetype` 负责体量与立面规则。新增形制不自动把普通建筑加入 20 处精选导航，也不改变稳定的拾取与资源标识。

### 5.2 解析、回退与异常处理

- [x] 普通建筑按字段应用“有依据的人工覆盖 → 有效 OSM 标签 → 形制默认值 → 通用默认值”，保留原始标签和最终采用理由。
- [x] 区分 OSM 数值有效性和字段是否存在；无效高度、层数进入明确的回退路径。
- [x] 若同时提供层数与高度，立面使用确认层数分层；检查平均层高是否合理，冲突进入报告，不再无条件用 `height / 3.3` 覆盖层数。
- [x] 原型只影响已有轮廓之上的生成；对食堂关闭宿舍式默认阳台，宿舍阳台也允许按立面禁用。
- [x] 有入口依据时使用校准入口；无依据时保留确定性的示意回退并标注，不能把自动朝向道路等同实景入口。
- [x] 未知 ID、重复键、非法数值、越界分段和失效锚点作为数据错误报告；缺少资料属于待核对状态，两者分开处理。
- [x] 现有独立地标、荟萃楼自定义模型、主席台及纪念柱等专用分支继续优先处理，首版普通楼覆盖表不接管这些对象。
- [x] 同步 `buildings.json`、GeoJSON 对应属性及统计，沿用 `heightBasis`、`facadeBasis`，避免页面显示旧依据。
- [x] 前端需要消费的新字段同步到 `lib/campus/types.ts`；纯建模字段留在数据与生成侧，复用已有按稳定 ID 生成的材质变体。本批新字段均由数据/建模侧消费，前端无需新增类型字段。

### 5.3 批量推进与验收

当前已建立 11 条部分校准记录及覆盖解析器，包含层数和主体高度校准、动物学院与数学学院多体量分段、农学院低门廊/内退入口，以及林学院和数学学院外挑雨棚；东苑、碧湖苑食堂补充了层数校准。整栋入口、主要立面或体量仍有待核对项，尚未达到本节整批完成标准，记录数量不等于整栋完成数量。详见[楼栋校准记录](BUILDING_CALIBRATIONS.md)。

先用 5–8 栋验证数据契约、生成效果和资料工作量，再分批扩展到 20–30 栋。每批记录“修改前 → 采用依据 → 修改后 → 未确认部分”，并在样板镜头中检查楼群与地标的高度比例。

完成标准：每栋完成层数/主体高度、屋顶、入口和主要立面的核对；无法确认项明确列出，至少一项有依据的形体或入口校准已落地才计入完成数。确认项、估算项、待核对项分别统计，不能把仍沿用默认值的整栋标为实测。

## 6. S3：图书馆北入口完整场地样板

当前已修复完整重建的外围道路/来源依赖及共享楼体身份问题，校正北门六柱数量，并依据方位资料修正南北体量与北向双回形幕墙；中央铺地连接、台阶下地形补片与前场排树已实现并通过源文件/实际 GLB 检查；日夜、图层、固定镜头、远近景及本批同条件性能复核通过。相邻普通楼栋校准仍未完成。见[样板记录](LIBRARY_NORTH_SITE.md)。

选择这里是因为已有图书馆分段体量、内院、北门资料和固定视角，适合建立可复用标准；不预设它是当前问题最多的地点。

**范围：** 图书馆北门门廊、平台、台阶或有资料支持的坡道、门前铺地、相邻校道、绿化边界，以及对样板构图影响最大的普通楼栋。S0 将范围落为明确多边形和对象清单，不采用无限扩大的周边半径。

**主要入口：** `blender/library.py`、`scripts/architecture_data.py`、`blender/build_campus.py` 的地形/铺地生成，以及现有道路派生数据。已新增 `data/site-overrides.json`、`scripts/site_data.py` 和 `blender/site_geometry.py`，分别保存人工参数、推导几何与生成模型。

首条记录使用 `library-north`，关联图书馆 `relation/11564702`，包含范围、坐标系、连接端点、标高基准、构件和来源。北门连接沿现有建筑局部轴线及其 `origin/angle` 转换，不按世界坐标的正北方向重新摆放入口。

- [x] 整理“道路 → 步道/前场 → 平台/台阶 → 门槛”的连接链，记录各接口位置和目标高程；复用现有北门，不重复生成门廊及台阶。
- [x] 将粗地形、结构性高差与防闪烁偏移分别表达。显示抬高 0.40/0.26 米不直接作为现实台阶高度。
- [x] 场地高程复用实际地形网格采样方法，必要时建立局部补片；补片边界接回原地形，避免以另一套插值产生接缝。
- [x] 在样板边界内明确替换哪些旧铺地，裁去重叠面并封闭可见侧边；道路支口保持开放，入口与通行区无树冠侵入。
- [x] 将 `site_data.py` 接入完整 `data:prepare` 的自动调用链。保留外围场地清理结果及 `surfaces` 数组槽位顺序：当前多套 `surfaceOverrides` 依赖数组索引，不能因样板裁面而重排。先读取最终既有道路/场地边界，再生成样板补片及替换映射，最后完成植被排除；完整建模读取同一份场地派生结果。
- [x] 将入口平台、路缘或挡墙等必要构件常驻基础模型，给每个构件明确所属图层和导出节点，避免地标近景替换后消失或重复。
- [ ] 对样板内相邻普通建筑应用 S2 校准，并核对主体与背景的比例。
- [x] 联合检查日间、夜景、关闭名称标签、基础/近景及图层开关；保存修改前后相同镜头截图。

样板验收必须同时满足：

1. 从相邻道路到门口的模型通行链连续；没有穿地、悬浮、铺面缺口、明显高差突变和共面闪烁。
2. 有意设计的台阶和挡墙有侧面与收口，推定尺寸有标注；不凭空补出无资料支持的无障碍坡道或设施。
3. 建筑既有内院、北门、道路开口及绿化留白保留；远近景不改变这些空间关系。
4. 对照参考资料检查去掉标签后的形体与空间组织，并记录人工判断，不能只以“更好看”验收。
5. 资产、固定视角性能与周边道路回归达到第 8 节要求，形成可复用的场地记录格式和检查流程。

## 7. S4–S5：按空间用途推广，最后细化

### 7.1 植被分区

先复用现有三种远近树模板，新增 `data/vegetation-zones.json` 表达有依据的空间规则；必要时将散布逻辑提取到 `scripts/vegetation_data.py`。

当前 S4 已接入两处 `no-tree` 配置、背景散点局部稳定化、最终贴地与统一占地/树冠筛选，并检查实际源文件和GLB中的建筑、道路、水体及运动场冲突，见[植被分区记录](VEGETATION_ZONES.md)。博萃路约120米的行道树试点已实现14株双侧树列，保留路口开口；逐项验收与估算边界见[试点记录](AVENUE_PILOT.md)。庭院和低矮景观仍未完成，下表继续表示完整目标范围。

| 区域规则 | 实施方法 | 验收重点 |
| --- | --- | --- |
| `no-tree` 开放区域 | 草坪、前场、入口和指定视线通廊设排除多边形 | 检查树冠范围，不能只检查树干中心 |
| `avenue` 行道树 | 有资料的道路侧线、间距及路口退让 | 保留入口、交叉口和支路开口，不自动扩展至全校 |
| `courtyard` 庭院/湖边 | 沿空间边界或少量明确点位配置 | 保留庭院、岸边步道、建筑主立面视线 |
| `background` 背景绿地 | 沿用受约束随机生成与固定种子 | 分区内可重现，局部修改不扰动全校树位 |
| `low-planting` 低矮景观 | 有资料时用独立低矮模板或实例表达 | 不以缩小乔木代替灌木、绿篱，也不凭空增加花坛 |

统一最终排除检查应在道路、桥梁、运动场和场地掩膜确定后执行，并作用于所有树位来源。继续保留 `clear_entrance_trees()`、运动场/篮球场/基础设施排树，以及 `campus_roads_data.py` 对汇学堂正东草坪 `way/822812174` 的树冠排除。不能因重新生成植被而让已清除的树回归。

2026-09-13 的[早期平面排除基线](model-checks/refinement/s4-final-exclusion-baseline.json)覆盖899个范围，树干冲突为零，504株保守树冠候选进入实际形体及标高核对。随后修复61株建筑穿插，当时保留3,050株；完整构建与道路/篮球场增量通过建筑表面净空验证，见[历史汇总](model-checks/refinement/s4-tree-clearance-summary.json)。后续已补充最终占地、模型保留区、闭合组件包含和实际场地检查；博萃路试点后的3,061株重新通过这些检查，当前证据见[行道树批次汇总](model-checks/refinement/s4-avenue-summary.json)。开放网格不自动封口，检查不等同于工程净空或全校实景种植调查。

规则重叠时，开放禁植区及道路/水体/运动场/入口硬排除优先，其次采用有依据的点位或行列，最后补充背景散点；分区互斥或对重叠树位去重，避免同一位置重复实例化。

分区来源、策略及估算参数保存在人工配置和检查报告中；首版尽量保持 `vegetation.json` 与前端实例化接口兼容。树木总数可增可减，完成指标是布局正确和留白得到保留。

### 7.2 场地推广与后期细节

镜湖靠大礼堂侧已实现[29.50 米岸段及陆侧过渡](SHORE_CALIBRATION.md)，源文件、实际 GLB 和图层画面检查通过，三轮活动数值达标但仍无法排除其他进程干扰，同条件性能验收仍待完成。2026-09-13 已实现 [6B 小广场铺地示例](PAVING_CALIBRATION.md) 的接缝、封口和穿地修复，并修复关闭道路后的地形纹理条带；实际几何、关联场地、七种图层画面及两条增量维护路径通过。铺地同条件性能验收仍待完成，其他岸段尚未推广。

样板通过后，选择一个有资料的代表性湖岸段和一处普通铺地边缘，分别验证“水面—岸坡/挡墙—岸顶步道”和“通用铺地—主路”连接。沿用现有水位与基础地形，不把全校湖岸统一替换为一种护岸。

材质、屋瓦、栏杆和装饰安排在形体与场地通过后。新增面数优先用于屋顶、入口、连廊、平台、挡墙和路缘；远处重复窗框与小构件继续简化。植被模板只有在布局校准后仍存在明确可见问题时再修改。

## 8. 验收与性能约束

### 8.1 数据和模型

| 检查层 | 必须验证的内容 | 建议落点 |
| --- | --- | --- |
| 数据 | 覆盖优先级、有效数值、来源引用、ID/锚点有效、原轮廓和内院保留、可重复生成 | 新增 `scripts/test_building_overrides.py`；扩展现有数据检查 |
| 形体 | 旋转矩形、内院、附楼、食堂无宿舍式默认阳台、基础/近景共享轮廓 | 新增 `blender/validate_generic.py` |
| 场地 | 实际网格上的接口高程、连续通行、补片接缝、铺面互斥、基础/近景不重复 | 新增 `scripts/test_site_data.py`、`blender/validate_site.py` |
| 植被 | 树冠排除、路口/入口退让、既有无树草坪、局部变更确定性 | 新增 `scripts/test_vegetation_zones.py` |
| 导出与加载 | 源 `.blend` 和解码后 GLB 的关键几何一致；区块覆盖、清单哈希及替换正常 | 复用现有导出验证方式和 `scripts/test-streaming.mjs` |
| 浏览器 | 固定镜头对照、LOD 往返、图层开关、搜索/巡游/分享、控制台和资源错误 | 扩展 `docs/VALIDATION.md` 并保存截图与版本 |

新增检查围绕真实风险和已知缺陷编写，不为本计划文档本身新增测试。容差应区分参数一致性、源几何误差和压缩误差；它们都不代表现实测绘精度。

### 8.2 性能

- 保持现有硬约束：`base.glb + trees.glb ≤ 6,000,000 bytes`，每个普通近景区块 `< 2,000,000 bytes`；脚本、JSON、解码器分别记录，不混入模型指标。
- 保留 `quality.ts` 的桌面 64 MiB、紧凑视口最多 32 MiB、流畅档 24 MiB 近景预算策略及既有前景地标优先逻辑；不为新增细节直接抬高预算。这是加载策略参数，不等于总显存上限。
- 使用 `scene.ts` 已有指标记录 FPS、三角形、Draw Calls、已加载资产、近景几何缓冲估算和首屏就绪时间；无需另建性能面板。
- S0 在同一设备、生产预览、固定视口和实际像素比下，分别建立精细/流畅档的持续活动基线。热身后执行相同 30 秒镜头运动，重复 3 次；冷缓存首屏另测，记录环境和加载稳定状态。
- 建议本轮采用相对回归门槛：同条件三次结果的 FPS 中位数下降不超过 10%，渲染三角形及 Draw Calls 增幅各不超过 15%。这是待实施的验收目标，不是现有实测结论；超出时先检查重复几何和非必要细节，保留真实测得的结果。
- 6pro 提到的约 439 万/142 万三角形仅作既有特定视角记录，不充当本轮基准。桌面手机尺寸模拟与手机真机结果分开记录；JS 堆和几何缓冲估算不称为独占内存或显存。

### 8.3 实施阶段命令

使用仓库现有工具链：Node.js 24、数据测试使用 Python 3.12，Blender 位于 PATH。依赖安装与快照恢复按 [MODELING.md](MODELING.md) 执行；默认复用现有快照，避免把数据更新和建模修复混在同一批。

```sh
# 修改数据规则后：在已安装 scripts/requirements.txt 的 Python 环境中执行
npm run data:prepare
npm run test:data

# 修改几何或数据后：完整同步源文件、基础与近景模型
npm run models:build

# 本轮入口/平台变更的道路碰撞检查，以及图书馆相关专项检查
blender --background --python-exit-code 1 --python blender/validate_road_buildings.py
blender --background --python-exit-code 1 --python blender/validate_architecture.py
blender --background --python-exit-code 1 --python blender/validate_landmarks.py

# 集成验收
npm run typecheck
npm run lint
npm test
npm run build:pages
npm run preview
```

新增专项验证脚本在实现后加入该流程。场地涉及道路接口或桥下区域时，补跑 `validate_bridge_joins.py`、`validate_infrastructure.py` 的对应检查；涉及运动场时补跑既有场地检查。`--base-only` 不用于本轮形体修改的最终交付，因为它不会同步全部近景和可编辑源文件。
